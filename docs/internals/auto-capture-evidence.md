# Auto-capture: what the evidence covers

Three different claims get confused constantly, so this file names them
separately: the event fires, the write survives, and a live store with a live
model completes a pass. All three now have evidence. The first two come from
tests and a real-host end-to-end run; the third comes from the maintainer's own
evidence files, checked 2026-11-24.

What has been established about auto-capture, by what kind of evidence,
and what remains unverified. The status and the arm/diagnose answer stay
in the README; this is the record behind them. The live counts below say what
ran and what passed the write gates. They are not a quality or billed-cost
benchmark.

## What has been established

What is established, from tests and fixtures (no live store involved):

- **The trigger events are ones the host actually emits.** Capture subscribes to `session.execution.succeeded` and `session.execution.interrupted`, the two turn-end events present in a recording of the desktop service (`test/fixtures/host-events.jsonl`). `session.idle`, `session.status` and `session.execution.failed` are *declared* by the host but absent from that recording, so they deliberately do not trigger capture; `test/identity/event-fidelity.test.ts` refuses a trigger that is only declared. An earlier revision subscribed to `session.idle` and stayed silent for days with no signal — reading a declared event as an emitted one is the failure that fixture exists to prevent.
- **The path runs under simulated host traffic** — unit tests hand the plugin the recorded envelopes and assert a candidate lands through the write gate, including conservation (a near-duplicate collapses at the gate instead of writing a second row): `test/capture/capture-auto.test.ts`, `test/capture/capture-compaction.test.ts`. The real-host scenario below covers the trigger itself; these tests pin the gate path under controlled input.
- **Identity triggers have their own recording check.** `test/identity/event-fidelity.test.ts` checks `IDENTITY_EVENT_TYPES` against the original 2.1.4 recording plus `test/fixtures/host-session-move.json`, a normalized one-frame extract from a separate 2.2.2 move capture. The extract must declare nonempty provenance and its retained envelopes must round-trip through the lockfile-pinned `@opencode/schema` 2.0.32 decoder. These checks reject missing metadata and malformed envelopes; they do not authenticate the capture. The identity replay uses the plugin subscription, but live plugin rebinding remains unverified. The recording version is distinct from the CI host pin (2.0.26).

- **Teardown stops work that is still in flight.** `generate.text` does not take the abort signal, so a capture parked mid-model-call used to wake up after the host disposed the plugin and run the whole write gate against a store its caller had already removed. Cleanup now aborts the subscription, every pass re-checks the signal after the model call and between candidates (a gate already mutating is never cut in half), and cleanup drains the tracked passes under a one-second bound — teardown never waits on the model. `test/capture/capture-dispose-drain.test.ts` parks a capture, disposes, releases, and asserts that no row and no evidence line carries a timestamp after disposal (#211).

- **The trigger is live on a real host, and the write now survives it.** An end-to-end scenario drives `opencode run` against a real turn with a scripted provider (`e2e/capture.test.ts`): the turn-end event fires and a capture pass starts, 12 of 12 runs. It used to reach the write gate in only some of them — 3 of 12 in one sample, 6 of 12 in a controlled A/B against the same script, 12 of 12 in two samples after the fix. `opencode run` disposes the plugin as the turn ends, and `captureCleanup` aborted every in-flight pass before its gate ran: the #211 contract, correct for the teardown it was written for and fatal here, because nothing is being torn down and the process simply exits. Cleanup now distinguishes the two cases — a pass still parked in the model call is abandoned, a pass that already holds its answer is drained, because its remaining work is local and milliseconds. All of #211's disposal assertions still pass unchanged. Fixed in #404; the 12/12 result is from after that fix.

- **The host abandons a turn-end handler that awaits; tying that to the original #406 misses is a hypothesis, not an observation.** Measured 2026-11-21 on opencode v2.3.0 (macOS) with a probe plugin over the same harness: the turn-end event reaches `event.subscribe` in 10 of 10 turns at every handler length, but a handler that awaits a timer records its completion in 0 of 10, and the plugin's cleanup fires 10 of 10. A reviewer's sweep put the abandonment boundary below 50 ms — a 50 ms, 200 ms and 2000 ms handler are all lost, RECV 10/10 throughout — so the claim is if anything understated. A write made synchronously as the handler's first action lands regardless. That is the measured mechanism: the host dispatches turn-end and exits without awaiting the handler. What is NOT measured is the identification of the issue's original natural misses (6 of 8, recorded 2026-11-13 on an older host) with this mechanism. Neither this work (45/45 before, 30/30 after) nor the reviewer (1 miss in 75 turns on v2.3.0, 24/24 under load) could reproduce a natural miss on the current host. So this repo adds observability to TEST the hypothesis rather than assert a cause: the pass writes `auto_capture_start` synchronously before the model call, so a pass that reached the model call but never recorded `capture_cost` is a visible cut; disposal writes `auto_capture_dispose` when an armed instance observed no turn-end event — a PREDICTIVE line, since the event is delivered in every measured run and an idle restart between turns produces it too. A deliberate skip writes `auto_capture_skipped` and no start line, so `memory_status` renders skip, cut, and never-fired apart. These are NOT all the states: a pass cut during the context read or the known-rows read — the awaited `loadAll()` before the receipt — writes no line of its own. The receipt trades that band (measured 0.72 ms at 200 rows, 2.08 ms at 2000, warm) for not misreporting a healthy skip as a cut; the `auto_capture_seen` arrival receipt in the next row names the band without moving the start line. Natural misses, when they recur, are then classified against these lines. `test/capture/capture-start-observable.test.ts` pins the receipt, the skip, the disposal flush, and the cut-outranks-dispose ordering.
- **A delivered event is named before it can be silently skipped.** At the dispatch head, a live idle subscription writes `auto_capture_seen` synchronously for each turn-end event it handles, before the loop's own skips can drop it. The receipt carries `discard=none|no_sid|cooldown`. The two discards name why no pass follows; `none` means the event proceeded toward a pass — so a `discard=none` line with no `auto_capture_start` and no later `auto_capture_skipped` makes the arrival-to-start band a named state, which `memory_status` can report ahead of never-fired. The warning compares the newest proceeding arrival in the window with the newest start or skip in that window. A tie withholds the warning, and earlier arrivals are not diagnosed individually. Attributed discards, and old stores with no arrival lines, render exactly as before. `test/capture/capture-arrival-receipt.test.ts` pins one receipt per handled event and that the arrival line rides first; `e2e/capture.test.ts` prints the arrived-lost count the start-retry masks.

- **The availability policy is measured against its alternatives, and against its own measuring stick.** `bun run bench:availability` (`bench/availability-results.md`) runs one capture pass over a 197-row store five times — no check, tag, drop-at-read (the P3 preview), delete-hardened (as shipped), and the original rule replayed from the pinned `362655c` module — with the byte budget swept over five sizes and the background resampled at 0/30/90/180 rows, because a claim measured at one budget or one store size is a claim about that budget. Tagging keeps all 10 new transport facts and retrieves 14 of 14 retrievable queries at every budget and every store size, where the original rule keeps 6 of 10 and retrieves 7 at every budget: that rule deleted four of ten new facts on a command mention alone, and a deleted fact cannot be retrieved. The ceiling is stated next to every recall figure and measured on the exact rows the arms retrieve: 14 of the 21 curated transport queries retrieve their own gold when that gold is the ONLY row in the store, so the tag arm's 14 is the achievable maximum and 9/21 was never 43% recall. The counterfactual is printed beside it — strip the keywords the capture reply carries and the ceiling falls to 9/21, because five of these pairs are retrievable only through the keyword list. A 25-case bank of every adversarial verdict this matcher has been found guilty of is re-decided on every run, one repo per case, and asserted in `bun test` because CI runs no bench. Writing those controls found two defects in the bench itself — verdicts keyed on `ts`, which is not unique when a pass writes rows in one millisecond, and a byte column summed across 21 queries and labelled per-block — and the corrected numbers are in the file. The report also states what it cannot measure: the check marks 6 of 16 rows a pass writes and 0 of 180 background rows, and that 0 is a fixture artefact rather than a base rate, because no seeded row quotes the tracked tree. It also tests the tag's justification directly: empty the tracked text and all 6 verdicts disappear, which is the property a read-time policy would keep and a delete would not.

- **The shipped availability consequence moved from tag to refusal.** A candidate whose every assertion the tracked tree states verbatim — modulo case, wrapping and markup — or whose only content is a command the project's gates declare, is refused at capture time and logged on `auto_capture_restatable` with the file or the gate named. The tag survives only as the retrieval demotion for rows written before the move; capture no longer writes it, and no refusal deletes anything from an existing store. The bench's `delete-hardened` arm is this policy: 10 of 10 transport facts kept, 6 of 6 restatable ones refused. `test/capture/capture-available.test.ts` pins the runtime consequence both ways — refusal lines with no row for the provable forms, kept rows for every veto the matcher owes — and the predicate fails open on every uncertainty (no git, unreadable file, capped scan, one new clause, one new figure), so the transport case is protected by construction. A pass's model-call cost is unchanged; what shrinks is the store and every later injection block. Decision: docs/adr/0009, superseding docs/adr/0008.

- **A live store with a live model completes the pass.** Counted from `~/.config/opencode/memory/evidence` on 2026-11-24, using only top-level `ev=` fields (quoted `tool_result` summaries that mention these names are excluded): `auto_capture_start` 205 lines, `capture_cost` 517, `capture_lag` 598, and `auto_capture_promoted` 1,193. The completion receipts cover 93 sessions; all six event types together cover 107 distinct sessions. The window runs from 2026-11-09T20:57:50.137Z through 2026-11-24T22:38:17.497Z. Twenty-nine sessions show the full start → cost → lag → promoted chain. The runs are mostly on `evo/Qwen3.8-Flash-Next-UD-Q4_K_XL`, with a few on `evo/gptoss`, `evo/ds4`, and `opencode/big-pickle`. There are also 15 deliberate `auto_capture_skipped` lines (all `transcript_too_thin`) and 20 `auto_capture_dispose` flushes with no turn-end event; those are not completions. Earlier checks on 2026-10-26 through 2026-10-29 found none, but that window predates the #404/#406 fixes on 2026-11-21 and the live-model sessions counted here. Reproduce the counts with:

  ```sh
  for ev in auto_capture_start capture_cost capture_lag auto_capture_promoted; do
    printf '%s ' "$ev"
    grep -h "^ev=$ev " ~/.config/opencode/memory/evidence/*.logfmt | wc -l
  done
  grep -h '^ev=capture_lag ' ~/.config/opencode/memory/evidence/*.logfmt \
    | sed -E -n 's/.* session=([^ ]*).*/\1/p' | sort -u | wc -l
  grep -hE '^ev=(auto_capture_start|capture_cost|capture_lag|auto_capture_promoted|auto_capture_skipped|auto_capture_dispose) ' ~/.config/opencode/memory/evidence/*.logfmt \
    | sed -E -n 's/.* (session|sid)=([^ ]*).*/\2/p' | sort -u | wc -l
  ```

## What has not been established

- A controlled quality or billed-cost figure for a live store. The receipts above prove execution and gate admission, not usefulness: they do not say how many rows a person would have written by hand, how many were noise, or what the provider charged. All 517 `capture_cost` lines carry `receipt=none`; `est_tokens` is derived from prompt size, not returned by the provider.
- A current trigger-timing benchmark. `bench/capture-trigger-results.md` is a **bench** simulation with a scripted extractor — its compaction world captured 0 rows and 4 of its 6 controls report FAIL. It answers "which moment is worth mining", not "does the shipped feature work".
